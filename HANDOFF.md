## Hard-won lessons (don't repeat these)

1. **CSS classes silently missing**: step 1 said it ported `lifeos.css` but several component-specific blocks (`.acct-*`, `.day-head`, `.tx-filter`, `.dl`, `.link-btn`, `.card-head`, `.qa-grid`, calendar `.cal*`, stats `.heat*`/`.trend*`) were *described* but never actually written to `app/globals.css`. This caused silent visual bugs (numbers running together, unstyled rows) that only showed up when the page was actually opened in a browser. **Before building a new screen, check whether the CSS classes it needs actually exist in `app/globals.css`** (`grep` for them) rather than assuming an earlier step ported everything from `design-reference/lifeos.css`. If missing, port them from the reference file (exact section is usually obvious from context).
2. **Server → Client Component props can't be functions.** Passing `monthLabel={(m) => ...}` from a Server Component page into a `"use client"` component throws at runtime (not caught by typecheck or build in dev mode — only surfaces when you actually load the page). Pass data, not functions, across that boundary.
3. **An HTML `<button>` can't contain another `<button>`.** `ActRow` (and anything similar) needs `role="button"` + `tabIndex` + `onKeyDown` on a `<div>` when a row has both a click-to-open-edit behavior *and* a nested action button (e.g. "pay now"). Only use a real `<button>` wrapper when there's no nested button. This is a hydration error, not a build error — only shows in the browser's dev overlay.
4. **Editing a computed balance double-counts transactions if you're not careful.** `accounts.opening_balance` / `cards.opening_used` are the stored fields; the *displayed* "current balance" is `opening_balance + sum(transaction effects)` via the `account_balances`/`card_usage` views. An edit form that shows the current balance and writes it straight back to `opening_balance` on save will double-count every past transaction. Fix: compute the delta between the new typed value and the current view value, and adjust `opening_balance` by that delta — see `lib/actions/accounts.ts` `updateAccount` and `lib/actions/cards.ts` `updateCard` for the pattern. Apply the same reasoning to any other field that's "stored baseline + accumulated effects" (there may be more of these in later steps — vehicle mileage is NOT one, it's just stored directly, but double check before assuming).
5. **The 5-second undo toast is basically untestable by clicking through the slow browser-automation tool.** Round-trips (screenshot → reason → click) routinely exceed 5 seconds, so the toast auto-dismisses before a "click undo" action lands, and the click falls through onto whatever's underneath (e.g. accidentally opening an account's edit form). This is a tooling-latency artifact, not an app bug — verify the undo *logic* by code review and by watching one successful toast render (confirms the message/button are correct), then verify the underlying mutation+inverse via direct SQL instead of chasing the click timing. Don't burn turns trying to "prove" undo works by clicking fast enough.
6. **Always clean up test data you create while verifying in the browser.** Several steps involved creating a test transaction/notification-ack via the UI to confirm a flow, then deleting it via `execute_sql` afterward so the seed data stays exactly reproducible (`select count(*) from transactions` should be 12 at rest; account balances should match the values printed in the step-2 summary). Check this before ending a step.
7. **Next 15.5.27 + Turbopack can't resolve `next/font/google`** in this environment (a real build error, not a sandbox-network issue — confirmed `curl` works fine). `npm run dev` / `npm run build` scripts were changed to plain webpack (no `--turbopack` flag) in step 1 for this reason. Don't add `--turbopack` back without re-testing a full build.

## Architecture patterns already established — reuse these, don't reinvent

- **Server Actions** live in `lib/actions/<entity>.ts`, one file per entity (`accounts.ts`, `bills.ts`, etc.). Pattern: zod-validate `FormData` → Supabase call (RLS does the `user_id` scoping, you never pass `user_id` yourself) → `revalidatePath(...)` the affected pages → return `{ id?, error? }` (create) or `{ error? }` (update/delete). Mutations that should support undo return enough of the *previous* state for an `undoX(...)` sibling action to restore it (see `payBillNow`/`undoPayBill` in `lib/actions/bills.ts`).
- **Domain logic** (pure, no I/O) lives in `lib/domain/*.ts`, ported from the matching `design-reference/lifeos-*.jsx` file, with a vitest file alongside (`*.test.ts`). CLAUDE.md requires this specifically for `lifeos-data.jsx`/`lifeos-store.jsx`/`lifeos-trips.jsx`/`lifeos-slips.jsx`; for step 6 the relevant reference files are `lifeos-things.jsx` (112 lines, assets+docs) and `lifeos-build.jsx` (209 lines, home+projects) — neither has been read yet. Skim them before building, same as every prior step.
- **Money display**: never format money server-side when the user might toggle "hide amounts" and expect it to update instantly. Use `<Money value={n} />` (`components/ui/money.tsx`) — it's a Client Component reading `usePrefs()`. `formatMoney()` (`lib/format/money.ts`) is the underlying pure formatter, fine for server-only text (e.g. calendar event subtitles, search result snippets) where instant hide-toggle isn't expected.
- **Date display**: `lib/format/date.ts` (`dShort`/`dLong`, Thai month names) for display; `lib/domain/dates.ts` for math (`addMonths`, `addCycle`, `occurrences`, `daysTo`, `dueLabel`); `lib/dates/today.ts` (`todayISOInBangkok()`) is the *only* sanctioned way to get "today" — never `new Date()` raw (CLAUDE.md rule, and it'd be wrong-timezone anyway).
- **Forms**: `components/ui/form-modal.tsx` (`FormModal`, `Field`, `FieldGrid`) is the shared shell. Entity forms live in `components/forms/*.tsx`, each a Client Component with local `useState` per field (no form library), calling the matching server action on save, showing a toast via `useToast()` (with an undo callback when the action is a fresh create), then `router.refresh()`.
- **Quick Add**: `components/providers/quick-add-provider.tsx` has a `KIND_META` registry array — add new kinds here (step 6 will want `asset`, `doc` at minimum; `lifeos-forms.jsx`'s full `QuickAdd` kind list is in the step-4 chapter if you need the complete target set).

- **Providers** (`PrefsProvider`, `ToastProvider`, `QuickAddProvider`) are mounted once in `app/(app)/layout.tsx`, which is an async Server Component fetching the current user's accounts/cards/prefs/notification-count up front and passing them down. If step 6 needs something available app-wide (e.g. a vehicles list for a global "add service record" quick-add), fetch it there.
